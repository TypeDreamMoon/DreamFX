## DFX7005

**Raised by** `Source/DreamFXEditor/Private/Generation/DreamFXGenerator.cpp:3789`, `Source/DreamFXEditor/Private/Generation/DreamFXGenerator.cpp:3794`
<!-- generated:end DFX7005 -->

**Cause.** R7 drift. The source did not change and the asset did not change, but a module they both depend on now exposes a different version -- so the asset was built against a different module than the one this build would use. Nothing in the source or the asset says anything about it, which is why the stamp records module versions.

**Fix.** Rebuild to adopt the new version, or pin the module with `@<version>` to have the mismatch reported at the call site. A warning by default because an engine upgrade hits every source at once and a rebuild resolves it; `-StrictVersions` makes it an error, for a release gate.

## DFX7105

<!-- generated:begin DFX7105 -->
**Severity** info

**Message**

```
pull: %s: %s -> %s
```

**Raised by** `Source/DreamFXEditor/Private/WriteBack/DreamFXPull.cpp:896`
<!-- generated:end DFX7105 -->

**Cause.** One literal the text writes differs from the value the asset stores for that input. The diagnostic's own
`file(line,col)` is the line the literal sits on, and the message gives `<module>.<input>`, the literal as written, and
what it would become. Raised once per literal by `dfx pull`; the value compared is the asset's rapid-iteration
**store**, not the resolved pin -- that distinction is the reason pull exists at all (`NS_Effects1_Mesh` stores
`Sprite_Atlas_Size.MeshYaw` = -90 while every read of the pin returns 0.0).

**Fix.** Nothing, unless you asked for it: without `-Apply` the run is a dry run and writes no byte. `dfx pull <file>
-Apply` writes them. Two things are worth checking when a line is a surprise: whether pull read the asset you meant
(an export names its mirror, so pulling the original's values needs `-Asset=`), and whether the asset stores this value
at all -- the run reports the store's own contents, and a text whose asset never held the value has nothing to pull.

## DFX7106

<!-- generated:begin DFX7106 -->
**Severity** info

**Message**

```
pull: %s is stored on the asset and not declared in this text -- skipped. pull adds no structure.
```

**Raised by** `Source/DreamFXEditor/Private/WriteBack/DreamFXPull.cpp:672`
<!-- generated:end DFX7106 -->

**Cause.** The asset's store holds a value for an input the text does not write. pull rewrites the literals a call
already has and nothing else: adding the argument would change the structure the text describes, which is a different
edit with a different owner -- the build safety gate (DFX8017) is what decides whether a rebuild would drop such a
value.

The list is long by nature. The engine materialises a constant for every input of every module, so most of these lines
are the module's own defaults sitting in the store; on this project's content one system reports 94 of them and 8 are
values someone actually tuned.

**Fix.** Nothing, when the value is the module's default -- a rebuild reproduces it and loses nothing, which is why
these lines are information and not a failure. When it is a tuned value (the ones DFX8017 refuses a save over), write
the input into the text and run pull again, or export with `decompile -NoDefaults`, which prints every input a module
has. Either way the next pull has a literal to correct.

## DFX7107

<!-- generated:begin DFX7107 -->
**Severity** info

**Message**

```
pull: '%s' already holds every value '%s' stores for the input(s) it declares (%d compared, %d not declared, %d not writable). No bytes written.
```

**Raised by** `Source/DreamFXEditor/Private/WriteBack/DreamFXPull.cpp:883`
<!-- generated:end DFX7107 -->

**Cause.** The comparison found nothing to write: every input the text declares and the asset stores a value for holds
the same value already. The comparison is by value, not by characters -- the text's literal is lowered exactly the way
a build lowers it and the bytes are compared against the store -- so `0` and a stored `0.0` are agreement and are not
rewritten into each other's spelling.

**Fix.** Nothing. This is the fixed point the command is built around: a second `-Apply` on a file that has just been
pulled reports this and writes no byte.

## DFX7108

<!-- generated:begin DFX7108 -->
**Severity** error

**Message**

```
pull reads a .dfs and the Niagara system it names: '%s' declares a %s document.
```

**Raised by** `Source/DreamFXEditor/Private/WriteBack/DreamFXPull.cpp:342`, `Source/DreamFXEditor/Private/WriteBack/DreamFXPull.cpp:356`, `Source/DreamFXEditor/Private/WriteBack/DreamFXPull.cpp:367`, `Source/DreamFXEditor/Private/WriteBack/DreamFXPull.cpp:381`
<!-- generated:end DFX7108 -->

**Cause.** pull needs a Niagara system to read values out of, and it takes the path from the text's own
`Name=`/`Root=` -- the same resolution a build uses, so that pull reads the asset this text writes. It fails four ways:
the file declares a Module, Emitter or DynamicInput document rather than a System; the root token does not resolve; no
system exists at the resolved path; or `-Asset=` named something that is not a Niagara system.

**Fix.** Build the text first when the asset has never been built, or name the asset you meant with `-Asset=`. Note
which asset an export names: plan-v4 writes every export into the `Decompiled/` namespace, so an export names its
MIRROR -- pulling the values someone tuned in the original is `-Asset=/Game/.../NS_X`, and that is also the only
spelling of it, since a `Name=` can only point at one of the two.

## DFX7109

<!-- generated:begin DFX7109 -->
**Severity** warning

**Message**

```
pull: %s: %s. pull rewrites literals inside a structure both sides agree on, so nothing in this stack was addressed.
```

**Raised by** `Source/DreamFXEditor/Private/WriteBack/DreamFXPull.cpp:465`, `Source/DreamFXEditor/Private/WriteBack/DreamFXPull.cpp:778`, `Source/DreamFXEditor/Private/WriteBack/DreamFXPull.cpp:805`, `Source/DreamFXEditor/Private/WriteBack/DreamFXPull.cpp:842`
<!-- generated:end DFX7109 -->

**Cause.** pull addresses an input by matching the text's statement to the asset's node at the **same position in the
same stack**, and refuses the whole stack when the two do not line up: a different number of nodes, a node that is a
module call on one side and a folded assignment run on the other, a module call whose asset is not the script that node
runs, an `as <name>` the asset's node does not carry, or an emitter or stack the asset does not have at all.

The refusal is the feature. A correspondence that might be off by one rewrites the wrong literal, and a wrong literal
in a text file is silent corruption -- the message therefore prints both sides' node names, which is also the diagnosis
one line further on.

**Fix.** Build the text, which is what makes the asset match what the text describes, then pull. When the two are meant
to differ structurally -- an edit that has not been built yet -- pull is not the tool for the values inside that stack.

## DFX7110

<!-- generated:begin DFX7110 -->
**Severity** error

**Message**

```
pull: the rewritten text does not read back (%s), so '%s' was left untouched.
```

**Raised by** `Source/DreamFXEditor/Private/WriteBack/DreamFXPull.cpp:927`, `Source/DreamFXEditor/Private/WriteBack/DreamFXPull.cpp:940`, `Source/DreamFXEditor/Private/WriteBack/DreamFXPull.cpp:948`
<!-- generated:end DFX7110 -->

**Cause.** The write half failed, and nothing was left half-done. The same code covers the three ways it can: the
rewritten text does not parse (pull parses its own output before touching the file, and splices only over the byte
range the parser recorded for the literal, so this is a defect in pull rather than in the text), the backup could not be
written, or the file itself could not be written.

**Fix.** Report it when the message says the rewritten text does not read back: the file on disk is exactly what it
was, and the byte range pull replaced is the only information needed to reproduce it. The other two are an environment
problem; when the last message names a backup, the bytes the file held are there.

## DFX7111

<!-- generated:begin DFX7111 -->
**Severity** info

**Message**

```
pull: %s is declared but was not written back: %s
```

**Raised by** `Source/DreamFXEditor/Private/WriteBack/DreamFXPull.cpp:589`, `Source/DreamFXEditor/Private/WriteBack/DreamFXPull.cpp:766`, `Source/DreamFXEditor/Private/WriteBack/DreamFXPull.cpp:825`
<!-- generated:end DFX7111 -->

**Cause.** The text declares the input, the asset stores a value for it, and pull still would not write it. Each line
names which of the reasons it is:

- the value is not a literal -- a link, a dynamic input, an `hlsl { }` block, a `curve { }`, a data interface or an
  object reference. Changing a value MODE is an edit, not a write-back;
- the text's value does not type-check against the input, which the build would refuse for the same reason;
- several inputs, or several arguments, share one identifier. The DSL drops spaces, hyphens and case, so the value
  input `Scale RGB` and the inline edit condition `ScaleRGB` that gates it are one name to this language. Which one a
  written value MEANS is decided by its type, the way the generator decides it; pull only reports when it cannot tell;
- the same parameter name is stored in two scripts with different values, so which copy the engine reads is not
  something pull can determine;
- the stored value has no spelling in this language (a struct that is not int/float/bool/2-4 packed floats);
- the stack is an `OnEvent` or `Stage` stack, which v1 does not address -- those are read through a focus slice, a
  different mechanism from the six fixed stacks.

**Fix.** Each line names its own reason, and the first two are about the text rather than the asset. For a shared
identifier, spell the intended input in a way that cannot be read as the other one, or change the value so its type
decides. For the event and stage stacks there is nothing to do in v1.
